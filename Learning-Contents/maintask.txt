   Intern Task Brief — Release Portal Security Gate (MVP)
 
   Hey! Welcome. This document is everything you need to get started. Read it end-to-end once, then start from Week 1.
 
   What you're building — in one line
 
   A small Python service that takes a GitHub Pull Request URL and returns a JSON verdict saying whether the PR is safe to release.
 
   Example:
   Input:  https://github.com/testmuai/some-repo/pull/123
   Output: {
     "pr_url": "...",
     "verdict": "block",
     "findings": [
       {"check": "secrets", "severity": "critical", "detail": "AWS key detected in src/config.py:42"}
     ],
     "scanned_at": "2026-07-02T10:15:00Z"
   }
 
   The Release Portal will call your service every time someone adds a PR URL for release. If the verdict is block, the release button is disabled.
 
   Why this matters
 
   Today, every release goes through a manual security review. Humans miss things — secrets in commits, wildcard IAM permissions, vulnerable dependencies. Your service catches these automatically, in under 60
   seconds, before a bad PR reaches production.
 
   If your service catches even one leaked AWS key over the next 6 months, it's already paid for itself many times over.
 
   Your scope — 3 checks only
 
   Do NOT try to build all 8 planned checks. Ship these 3 solidly:
 
   1. Secrets check — Are there any AWS keys, private keys, passwords, or API tokens in the code the PR is adding?
   2. IAM wildcard check — Does the PR add Action: "*" or Resource: "*" in any Terraform / IAM JSON file?
   3. Vulnerable dependency check — Does the PR add a new library (in go.sum, package-lock.json, requirements.txt, etc.) that has a known critical or high CVE?
 
   The other 5 checks are the mentor's job after your MVP is working.
 
   GitHub repo setup — Day 1
 
   Create a new repo under your personal GitHub account (mentor will fork to org later):
 
   Repo name: release-portal-security-gate
   Visibility: Private
   License: none for now
 
   Clone locally, then create this structure:
 
   release-portal-security-gate/
   ├── README.md              ← what the tool does, how to run it
   ├── requirements.txt       ← python deps
   ├── .gitignore             ← standard python .gitignore
   ├── .env.example           ← template for env vars (never commit .env)
   ├── src/

   │   ├── main.py            ← the CLI entrypoint
   │   ├── github_client.py   ← fetches PR data from GitHub API
   │   ├── checks/
   │   │   ├── __init__.py
   │   │   ├── secrets.py     ← check #1
   │   │   ├── iam.py         ← check #2
   │   │   └── cve.py         ← check #3
   │   └── verdict.py         ← combines findings into final JSON
   ├── tests/

   Week-by-week plan
 
   Week 1 — Foundations + Check #1 (Secrets)
 
   Goal: run python src/main.py <pr_url> and get back a JSON with any secrets found.
 
   Day 1–2:
   - Set up the repo above.
   - Create a GitHub Personal Access Token with repo read scope. Save it in .env as GITHUB_TOKEN=.... Never commit this file.
   - Write github_client.py: given a PR URL, fetch the PR's diff using the GitHub API. Endpoint: GET /repos/{owner}/{repo}/pulls/{pull_number}/files. Return a list of (filename, patch_text) tuples.
 
   Day 3–4:
   - Install the tool detect-secrets: pip install detect-secrets.
   - Write checks/secrets.py: take the diff, run detect-secrets on the added lines only (the + lines), return a list of findings.
   - Findings shape: {"check": "secrets", "severity": "critical", "file": "...", "line": 42, "detail": "..."}.
 
   Day 5:
   - Wire it all together in main.py. CLI: python src/main.py <pr_url> prints JSON to stdout.
   - Write 2 tests using a sample PR diff you saved in examples/.
   - Demo to mentor on Friday.
 
   Week 2 — Check #2 (IAM wildcards)
 
   Goal: catch Action: "*" or Resource: "*" in added lines of .tf or IAM JSON files.
 
   - Write checks/iam.py. For each file in the diff:
     - If the filename ends in .tf or looks like an IAM policy JSON, scan the added lines.
     - Use a regex first to find candidates ("Action"\s*:\s*"\*"), then verify.
     - Skip lines that are inside comments.
   - Return findings with the file + line number.
   - Write 3 tests: one true positive, one false positive (wildcard in a comment), one clean file.
 
   Week 3 — Check #3 (Vulnerable dependencies)
 
   Goal: detect new dependencies in the PR that have a known CVE.
 
   - Focus on requirements.txt and package-lock.json for the MVP. Ignore go.sum for now — Go modules are trickier.
   - For each added line in requirements.txt, extract (package, version).
   - Query the OSV.dev API: POST https://api.osv.dev/v1/query with {"package": {"name": "...", "ecosystem": "PyPI"}, "version": "..."}.
   - If OSV returns any vulnerabilities with severity HIGH or CRITICAL, flag it.
   - Cache results locally (a JSON file is fine) so you don't re-query the same package.
 
   Week 4 — Package + wrap up
 
   - Add a small Flask endpoint: POST /verdict that takes {"pr_url": "..."} in the body and returns the JSON verdict. This is what the portal will eventually call.
   - Write a good README explaining: what it does, how to install, how to run, how to add a new check.
   - Demo to mentor + DevSecOps team.
 
   What "done" looks like
 
   By end of week 4, you should be able to demo this end-to-end:
 
   1. Someone opens a PR that adds an AWS key to a Python file.
   2. You run curl -X POST http://localhost:5000/verdict -d '{"pr_url": "..."}'.
   3. Within 30 seconds, the response is {"verdict": "block", "findings": [...]}.
   4. Same for an IAM wildcard PR and a vulnerable-dependency PR.
 
   If those 3 demos work, you've shipped.
 
   Rules of the road
 
   - Read-only. Your tool never writes to GitHub, never triggers deploys, never modifies anything. It just reads the PR diff and reports.
   - No secrets in commits. Anything in .env stays in .env. If you accidentally commit one, tell your mentor immediately — do not try to hide it.
   - Small PRs. Each check gets its own PR against your repo. Don't push 3 weeks of work in one commit.
   - When stuck, ask. If you're stuck for more than 2 hours, message your mentor. It's not a failure — it's the point of an internship.
   - Pin your dependencies. In requirements.txt, always write package==1.2.3, never just package.
 
   Where to ask questions
 
   - Daily standup (15 mins): what did you do yesterday, what will you do today, blockers.
   - Slack: DM your mentor for quick questions. Post in #sec-tooling for design questions.
   - Weekly 1:1: 30 minutes with your mentor to go deeper.
 
   Short reading list (in order)
 
   1. GitHub REST API for pull requests: https://docs.github.com/en/rest/pulls/pulls (skim, then bookmark)
   2. detect-secrets docs: https://github.com/Yelp/detect-secrets — how it works, what it catches
   3. OSV.dev API docs: https://google.github.io/osv.dev/api/
   4. OWASP Top 10 — A01:2021 Broken Access Control (one-page summary is enough)
 
   Don't try to read everything before writing code. Read one section, write code, come back to reading.
 
   How you'll know you succeeded
 
   - Your service catches every AWS key I plant in a test PR.
   - Your service catches an obvious Resource: "*" in a Terraform file.
   - Your service correctly flags requests==2.20.0 as vulnerable (it has a known CVE).
   - Someone else on the team can install your tool from the README and run it without asking you.
 
   That's the bar. Ship that and we go from there.
